# BotSquad Multi-Agent Coordination Risks

## 1. Authority drift through prompts, messages, or delegated workers

- **Why it matters:** BotSquad’s product model depends on separating communication from authorization: messages communicate, tasks authorize bounded work, and trusted code enforces permissions. The architecture also states that child capabilities must remain within the manager’s delegatable capabilities and the company ceiling. If this boundary weakens, agents could appear to approve, expand, or execute work they were never authorized to perform. Evidence: `PROJECT_VISION.md` / Product principles; `AI_ORGANIZATION_MODEL.md` / Authority ceiling; `SYSTEM_ARCHITECTURE.md` / Authority and tool identity; `decision_004_delegated_worker_creation.md` / Decision.
- **Likely failure mode:** A manager creates a specialist with overly broad text instructions, or sends a message that implies extra permission; the child treats that as authority and attempts protected actions, causing unsafe behavior or confusing audit history.
- **Concrete mitigation:** Keep all authority decisions in validated control-plane operations; reject unknown tool fields; enforce `child effective capabilities ⊆ manager delegatable capabilities ⊆ company ceiling`; make approval-gated/human-only operations impossible to grant by text; add tests for prompt/message privilege escalation and worker-creation escalation.

## 2. Duplicate, lost, or incorrectly replayed work across dispatcher/runtime boundaries

- **Why it matters:** Reliability goals require no lost messages, no duplicate tasks, no repeated completed work, and recoverable restarts. BotSquad separates durable tasks from Codex runtime threads, uses event-driven dispatch, and supports restart recovery; that boundary is complex and central to coordination correctness. Evidence: `PROJECT_VISION.md` / Success metrics; `SYSTEM_ARCHITECTURE.md` / Task and worker lifecycle, Event-driven dispatcher, Restart, ownership and recovery; `README.md` / Architecture and Current limits.
- **Likely failure mode:** A crash or duplicate event leaves a parent waiting forever for a child result, starts two executions for one worker/task, or replays a completed child assignment after restart, producing conflicting artifacts and manager decisions.
- **Concrete mitigation:** Preserve transactional task/execution state transitions, unique running-execution constraints, idempotency keys for tool receipts and child-result linkage, startup reconciliation for orphaned executions, and explicit human-inspected retry rather than automatic replay. Continue real end-to-end restart validation for Human → Atlas → Scout → Atlas.

## 3. Evidence and artifact trust gaps

- **Why it matters:** The system’s decisions are supposed to be inspectable and evidence-based, with artifacts attributable to producing executions. If artifact provenance, integrity, confinement, or context selection fails, managers and humans may rely on stale, tampered, oversized, or irrelevant evidence. Evidence: `PROJECT_VISION.md` / Product goals and principles; `SYSTEM_ARCHITECTURE.md` / Persistent domain, Codex adapter, Restart, ownership and recovery; `README.md` / Current limits.
- **Likely failure mode:** A report is stored without reliable execution linkage or integrity verification, a crash leaves confusing artifact state, or a resumed manager receives incomplete/misleading child evidence and makes an unsupported recommendation.
- **Concrete mitigation:** Keep controlled artifact submission only; bind artifacts to task and execution IDs with hashes; serve artifacts after confinement/integrity checks; include bounded child-result and artifact references in review context; surface missing/corrupt runtime or artifact state visibly instead of silently rebinding or proceeding.
